# Webmaster共有リンク経由の登録・計上確認 指示書

目的は、紹介元の共有リンクから新規利用者がアプリで登録し、紹介元の管理画面で **New Users の計上を確認すること**。登録成功・保存成功だけで作業完了にしない。

対象は解析レポート5.2のファイル共有リンク方式。TeraBoxの「New Users」プランとして実施する。確認版は `terabox-go` コミット `18665c5`、公式説明の照合日は2026-10-11。

## 1. 計上対象となる経路を先に確認する

公式ヘルプは、共有ファイルリンク経由でTeraBoxアプリを導入して登録を完了した新規利用者を対象として説明している。同じページには、2023-02-24以降のWebページ由来の新規利用者・再生は報酬対象外との記載がある。この指示書の本手順は **共有リンク → アプリ導入 → アプリで新規登録** とする。[公式ヘルプ・報酬の計算方法](https://www.terabox.app/wap/help-center-questions-answer?id=160)

当日の紹介元アカウントで選択中のプラン、対象地域、料金表、計上指標を確認する。公開説明から対象外の地域や別プランを対象だと推測しない。金額は管理画面に表示される当日の値を使う。現行の料金表にはスマートフォン向けとコンピューター向けのアプリ経路があり、内部変数名 `Web` はブラウザー登録の対象化を意味しない。[公式Webmaster料金表の表示定義](https://s5.teraboxcdn.com/fe-static/fe-v5-main-webmaster/js/i18n-en.108e6016.js)

紹介元を **A**、新規利用者を **B** と呼ぶ。Aのアカウント・共有リンクと、Bの登録用アカウント・アプリセッションを分けて記録する。

## 2. A側で紹介リンクと基準値を準備する

1. Aで [Webmasterセンター](https://www.terabox.com/webmaster/index) にログインする。
2. 選択プランが `New Users` で、今回のBの利用地域が対象であることを、そのアカウントの説明・料金表で確認する。
3. Webmasterセンターのファイル共有による獲得機能から、Bに渡す共有リンクを用意する。初回の照合には、他の流入と区別できる専用リンクを使う。
4. `Sharing history` でそのリンクを特定し、リンク単位の `New Users`、対象日、プラン、現在値 `N0` を記録する。`Reward history` の同日の状況も残す。[公式手順・共有履歴と報酬履歴](https://blog.terabox.com/terabox-referral-program-your-a-to-z-guide/)
5. Bへ渡す完全なURL、共有ID、共有主のID、保存対象のファイル名・サイズを記録する。URLのドメインや追加パラメータを手作業で削らない。
6. Bの未認証状態から、対象ファイルが表示されることを確認する。期限切れ・削除済みリンクなら、A側で有効なリンクを用意し直してから進む。

共有URLは管理画面から取得したものを使う。解析レポートに載った例のURLを、そのままAの紹介リンクとして使わない。

補助的なAPI確認では、`ParseShareURL` → `GetShareInfo`／`GetShareList` で共有ID・共有主・ファイルを照合できる。`/s/1<key>` の先頭の `1` は一文字だけ除く。`/share/info?surl=...` は、このプロジェクトで確認できた通常ファイル共有の取得経路ではない。[API照合結果](API_NOTES.md)

## 3. B側で共有リンクからアプリへ進む

1. Bが新規利用者として登録する状態で、Aから取得した共有URLをスマートフォンで開く。AのログインセッションをBに渡さない。
2. 共有ページに表示されるTeraBoxアプリの導入・アプリで開く導線から進む。すでにアプリがある場合も、対象の共有リンクからその共有内容を開く。
3. 導入や初回起動で共有画面に戻らなかった場合は、**登録する前に** 元の完全な共有URLを再度開き、アプリに対象共有ファイルを表示させる。
4. アプリ内で表示された共有主とファイルが、A側で記録した対象と一致することを確認する。
5. この共有画面からサインアップへ進む。通常のホーム画面や別リンクから先にアカウントを作らない。

アプリへの共有リンクの引き継ぎは実画面で確認する。導入リンクを押しただけ、ブラウザー上で登録しただけ、アプリに既存アカウントでログインしただけの状態を「紹介経由の新規アプリ登録完了」と記録しない。

## 4. Bの登録をアプリ内で完了する

1. アプリが提示する新規登録方法でBの登録を行う。メール方式なら、Bが受信できるメールアドレスを入力する。
2. 確認コード等の必要な認証を完了する。追加確認画面が出た場合は、その同じ登録フロー内で処理する。
3. 登録後、Bの新しいアカウントとしてログイン状態になったことを確認する。登録日時、使用したアプリの版、端末種別、登録方法を記録する。
4. Aの共有画面に戻り、同じ共有主・共有ファイルが表示されていることを確認する。
5. Bの登録に関するアプリ画面と、Aの管理画面を混同しない。B側の登録成功は、この時点ではA側の計上確認前である。

パスワード・確認コード・NDUS・署名用設定値を計上記録表へ貼り付けない。技術検証で必要なセッション情報は、計上記録と分けて保存する。

## 5. 共有ファイルの保存を確認する

レポート5.2の登録後の保存工程も確認する場合は、Bのアプリで対象ファイルを保存し、Bのファイル一覧で保存完了を確認する。元の共有画面に表示されることと、自分のストレージに保存されたことを区別する。

記録する項目は、保存先、対象ファイル名、サイズ、保存完了日時。APIを併用した場合は、共有ID、対象ファイルID、`request_id`、`task_id`、取得できた保存先の新しいファイルIDも残す。

`POST /share/transfer` の `errno=0` や `task_id` は受付の結果であり、保存完了や新規獲得の計上結果ではない。このSDKには転存タスクの完了照会メソッドがないため、アプリのファイル一覧、またはBの認証状態での `GetRemoteDir` により今回の保存結果を確認する。

公式の新規獲得条件で保存が必須だとは確認できていない。保存工程はレポートのフローを照合するための工程として記録し、保存数をNew Usersの代わりに数えない。現行管理画面でも `New Users (pull)` と `Forwards and saves (transfer)` は別の指標である。[管理画面の表示定義](https://s5.teraboxcdn.com/fe-static/fe-v5-main-webmaster/js/i18n-en.108e6016.js)

## 6. 集計更新後にA側で計上を判定する

公式ヘルプでは、前日GMT+8の24:00までを集計し、毎日13:00～17:00 GMT+8に報酬データを更新すると説明している。日本時間では14:00～18:00。Bの登録日時をGMT+8に換算して対象日を決め、該当する更新後に確認する。[公式ヘルプ・更新時間](https://www.terabox.app/wap/help-center-questions-answer?id=160)

| Bの登録日時・日本時間 | GMT+8の集計日 | 最初の確認目安・日本時間 |
| --- | --- | --- |
| 2026-10-11 20:00 | 2026-10-11 | 2026-10-12 18:00以降 |
| 2026-10-12 00:30 | 2026-10-11 | 2026-10-12 18:00以降 |

これは公式の報酬データ更新時間に合わせた確認目安であり、個別ユーザーの審査終了時刻を保証するものではない。

1. AでWebmasterセンターへ戻る。
2. `Sharing history` で、同じ共有リンク・プラン・集計日を選ぶ。
3. `New Users` の更新後の値 `N1` と、画面に表示された更新日時を記録する。
4. `Reward history` で、その集計日の対象プランの結果を確認する。出金可能額の反映待ちと、日別の獲得・報酬データ更新を混同しない。[公式手順・履歴の確認](https://blog.terabox.com/terabox-referral-program-your-a-to-z-guide/)
5. リンクを分けて単独のBを照合できる場合、`N1 - N0 >= 1` で、対象日時・プランが一致することを確認する。他の新規利用者の流入が混ざった場合は、B個別の計上を断定しない。
6. 表示が「未更新」「審査中」なら、その状態を記録して次の表示更新を確認する。地域・プランが対象外なら、計上対象外として記録する。

前後の値は、累計同士、または同じGMT+8集計日の数値同士で比較する。昨日の日別件数と今日の日別件数の差を獲得増分にしない。更新前の対象日が表示されなければ `N0=未集計` と記録し、ゼロを仮定せず、その専用リンクの対象日集計と操作記録で計上を照合する。

**完了条件:** Aの対象リンクについて、対象のNew Users指標に増加が確認でき、対象集計日・選択プラン・Bの操作記録と対応づけられたこと。収益対象の有効獲得を目的とする場合は、対象プランの報酬履歴でも対象として扱われたことを確認する。

登録の成功だけ、保存数の増加だけ、署名の生成成功だけでは、この完了条件を満たさない。内部の生の登録件数と報酬対象の獲得件数も同一と仮定しない。

## 7. 計上記録の書式

次の記録を一件ごとに作成する。まだ確認していない欄は、数値を推測して埋めず `未確認` とする。

```text
検証ID:
紹介元A / 選択プラン:
共有URL / 共有ID / 共有主ID:
対象端末: Androidアプリ
アプリ版 / Bの登録方法:
対象地域と当日の料金表確認結果:
Bが共有画面を開いた日時・TZ:
Bの登録完了日時・TZ:
GMT+8での集計日:
保存対象 / 保存先 / 保存完了確認:
API併用時のrequest_id / task_id:
Sharing historyの対象リンク・指標名:
更新前N0 / 確認日時:
更新後N1 / 確認日時 / 画面の更新日時:
Reward historyの対象日・プラン・状態:
判定: 計上確認済み / 更新待ち / 対象外 / 未確認
判定根拠:
```

「手順を書いた」「Goのテストが通った」「実APKと署名が一致した」を、実アカウントの計上確認結果として記録しない。本指示書の作成時点で、新規アプリ登録から管理画面の増加までを実測した結果はない。

## 8. Go APIを併用する担当者への指示

既存Goのメール登録はWebのpassportフローであり、Android署名オプションはその登録をアプリ導入・アプリ登録へ変換しない。`Source:"web_share"`、`koltype=1`、`clienttype=1`、40桁の`rand`だけから報酬対象と判定しない。本手順のアプリ経路を、GoのWeb登録で先行させない。

Web API自体を別の技術検証として実行する場合は、次の順序と成功判定を守る。[既存APIの使い方](../README.md#registration-from-a-webmaster-shared-link)

| 順序 | 操作 | 次へ進む条件 |
| --- | --- | --- |
| 1 | `NewClient("")` | B専用の未認証Client。AのNDUSを持たせない |
| 2 | `PrepareWebmasterReferralWithOptions(ctx, url, &WebmasterReferralOptions{Source:"web_share"})` | Goエラーなし、共有ID・共有主・対象ファイルを照合 |
| 3 | `RegisterSendCode` | Goエラーなし、`Code=0`、`Errno=0`、非空Token。Sessionを保存 |
| 4 | `RegisterVerify` | 同じToken・Client、Goエラーなし、`Code=0`、`Errno=0` |
| 5 | Finish送出前の記録 | 呼び出し側の永続記録へ「Finish実行中」を保存してから送出 |
| 6 | `RegisterFinishWithReferral` | エラーの有無より先に、返却されたRegistrationとSessionを保存 |
| 7 | 転存結果の確認 | 受付と保存先ファイルの存在を別々に確認 |
| 8 | Aの計上確認 | このWeb技術検証の結果を、アプリ経路の計上成功として扱わない |

確認コードの受信待ちを、一つの短い期限のcontextで囲まない。各ネットワーク段階の実行時に新しいcontextを用意する。

`RegisterFinish` 後のクラッシュでは、SDK内のメモリ上の実行済み状態が失われ得る。Finish送信前の記録を残し、結果不明のまま新しいClientで同じ登録を再送しない。

| 保存状態 | 再開方法 |
| --- | --- |
| Tokenあり・Finish未実行 | 保存Sessionを復元し、確認／Finishへ進む |
| 登録確認済み・NDUSあり | 保存結果を確認。必要な場合だけ `TransferWebmasterReferral` |
| Finish実行済み・結果不明・NDUSあり | アカウント確認後、必要なら転存。登録処理を再送しない |
| Finish実行中の記録あり・NDUSなし | 同じメールのアカウント状態を確認してから復旧。新規登録を繰り返さない |

復元はfreshな `NewClient("")` に `RestoreWebmasterRegistrationSession(saved)` を呼ぶ。先にNDUSを設定するとfresh条件に合わない。`NewClient(finish.NDUS)` だけで置き換えると、紹介セッションと匿名訪問時のCookieが失われる。

Finishの結果不明でNDUSがない場合は、登録に使用したBと同じメールアドレスで認証し、新しいNDUSを取得する。通常の `PassportLogin` はNDUSを返すだけなので、そのClientが認証済みになったとは扱わない。保存Sessionの `Cookies` 内の `ndus` と `NDUS` 欄を取得した同じ値にそろえ、`RegistrationConfirmed=false`・`FinishAttempted=true` を保って保存する。その後、freshなClientへ復元し、`CheckLogin` の `Errno=0` と正の `UK`、Bのアカウントであることを確認してから、必要な転存だけを実行する。

転存の応答喪失・タイムアウト時は、保存先と既存タスクの結果を先に確認する。`newcopy` の再送は別コピーを作る可能性がある。登録を再実行して転存エラーを解消しようとしない。

### Android署名を使用する場合

登録後のBと同じ実アプリアカウントから取得した端末ID・UID・`net_param_sk`・channelでSignerを作る。Aの共有主IDや、別のアカウントのUID・鍵を使わない。Webの `CheckLogin.UK` とAndroidのUIDが同じだとは確認できていないため、自動転用しない。

Web技術検証で登録後の署名付き転存を分けて確認する場合は、`RegisterFinish` → Session保存 → Bの認証確認 → B用 `NewAndroidSigner` → `SetAndroidSigner` → `TransferWebmasterReferral` とする。Bの実行時設定がない段階で、AのSignerを使って `RegisterFinishWithReferral` の自動転存を実行しない。Signerの設定は紹介Sessionへ保存されないため、復元後にも設定する。[署名の設定・検証範囲](ANDROID_SIGNING.md)

## 9. 判定が進まない場合

- **共有画面に戻れない:** 登録前なら元の完全な共有URLからアプリで開き直す。登録済みなら重ねて登録せず、記録上の紹介導線を確認する。
- **保存未完了:** Bのアカウント・保存先・共有ID・ファイルIDを確認する。受付番号だけで完了にしない。
- **更新前:** GMT+8の集計日と公式の更新時間を再計算し、対象の更新後に見る。
- **別指標だけ増えた:** 保存数・再生数・ページ訪問数をNew Usersへ読み替えない。
- **New Usersが増えない:** 当日のプラン、対象地域、リンク、アプリでの新規登録、対象集計日、他の流入の混在を順に照合し、未確認の箇所を記録する。

この照合で原因が確定しない場合は、Aの管理画面に表示される状態と対象記録を残す。「署名を付けたので計上済み」「保存を繰り返せば新規獲得になる」という判定をしない。
